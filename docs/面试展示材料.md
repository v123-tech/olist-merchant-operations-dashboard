## 九十秒项目介绍

我做了一个商家经营与订单履约工作台的个人项目，希望把“发现经营异常”推进到“找到订单、理解原因、记录跟进”的完整流程。

数据来自 Olist 公开历史数据，共 99,441 笔订单。我先梳理订单、商品、付款和评价粒度，核对晚收货分母。业务发现窗口有 83,696 个有效妥投订单，其中 5,930 单晚收货，比例 7.09%；月份和地区差异说明只看整体比例不够。

产品包含经营概览、履约工作台和规则验证三页。工作台按历史时点显示已见事件，用 R1—R4 截止规则提供核查原因，支持浏览器内模拟处置。8 月留出样本中，交运规则提前覆盖 246/351 个晚收货订单，但提示命中比例只有 17.18%，因此我把处理负担也作为重要验证内容。

我主要负责问题定义、需求梳理、指标检查、功能验收和反馈，AI 参与代码实现与迭代。当前可以证明流程与历史计算的可复核性，没有真实商家采用或降延误效果；下一步应做用户任务观察和授权试点。

作品集已通过 [公开 HTTPS 链接](https://olist-merchant-workbench.luozilong888.chatgpt.site/)演示，访客无需安装或登录。上线表示作品可直接体验，不表示已被真实商家采用。

## 面试追问

| 问题 | 回答要点 |
|---|---|
| 为什么做这个项目？ | 希望展示将数据发现转成需求、流程、交互和验证的能力。经营指标只是起点，运营还需要知道检查哪一单及如何记录跟进。没有虚构真实商家提出过需求。 |
| 为什么选 Olist？ | 其官方公开数据包含订单、商品、付款、评价及履约里程碑，适合练习多表粒度、指标口径和历史事件回放；公开匿名历史数据不等于当前中国商家需求。 |
| 如何发现核心问题？ | 先核对订单与金额没有被一对多连接放大，再比较月份和地区的数量、比例与分母。7.09% 只是总体，RJ 与 SP 的对照推动了下钻设计。 |
| 晚收货率怎么定义？ | 分子为实际收货日期晚于承诺日期的订单，分母为时间有效的已妥投订单；同日按期，未妥投和时间无效不可判定。承诺按当日结束，即次日 00:00 的不含边界处理。 |
| 为什么先用规则而不是机器学习？ | 现有里程碑和截止时间能支持可解释的检查动作。用户任务、处理成本与实时数据质量尚未验证，先建立规则基线；未来若负担高，再评估模型是否改善决策。 |
| 命中与覆盖为什么要权衡？ | 覆盖高但提示量过大，会增加人工检查负担。交运规则覆盖 70.09% 同时只有 17.18% 的提示最终晚收货，应披露两者和样本量，再测可行动率与每单耗时。 |
| R3 覆盖 100% 是预测能力强吗？ | R3 是承诺前 24 小时仍未收货的截止监控。最终晚收货订单在该时点尚未收货，高覆盖主要来自定义及完整事件假设，不能包装成模型准确率。 |
| 你本人做了哪些工作？ | 主要负责问题定义、需求梳理、指标检查、功能验收和产品反馈。面试展示自己实际理解、复核和操作过的证据；不声称独立手写全部代码或有企业 PM 任职经历。 |
| AI 具体做了什么？ | AI 参与 Python/SQL、页面、浏览器计算适配和文档迭代。工具生成需要人工理解、口径核查和验收，不能把生成代码本身当作个人独立研发证明。 |
| 怎样核验 AI 输出？ | 看真实源文件和 SQL，直接从原始 CSV 重算关键分母与金额；对照原 Python 与静态计算；用规则边界和未来字段扰动检查；最后手动完成筛选、详情、保存刷新和重置。只陈述本次确实执行的检查。 |
| 怎么避免历史回放泄漏？ | 事件仅在记录时间小于等于观察时点时可见，静态属性批准后假设已知；未来收货、最终状态和评分不参与触发。公开资源仍含完整历史，遮蔽用于业务模拟而不是保密。样本筛选依赖事后信息，选择偏差另行披露。 |
| 为什么选静态部署？ | 历史数据固定、处置无需跨设备同步，静态托管减少服务休眠、磁盘持久化和账号维护。保留完整交互的代价是首次完整查询需要下载约 15 MB 压缩数据，并占用浏览器内存。 |
| 网站真正上线了吗？ | 已部署为无需登录的公开 HTTPS 作品集，链接见 README，核心筛选、回放与模拟处置已在公网核对。源码仓库上传状态另行披露。网站上线只代表作品可访问，不表示系统被真实商家使用。 |
| 模拟处置会互相污染吗？ | 按网站源和浏览器配置文件保存于 localStorage；不同配置文件不共享。同一配置文件多标签页共享；刷新可恢复，可一键重置。不是账号身份隔离或跨设备同步，不能用于真实多人业务。 |
| 与商用系统差多少？ | 缺真实需求访谈、实时事件和上报延迟、承诺修改历史、包裹级归属、权限审计、协同通知、监控与业务试点。下一步先验证任务能否完成及提示是否可行动，再决定需要哪些系统能力。 |
