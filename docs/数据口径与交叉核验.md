# 数据口径与交叉核验

## 输入与边界

本版从私人环境中的官方版本二原始压缩包只读计算，使用全部99,441笔订单和112,650条商品行。原始包为44,717,580字节，固定SHA-256为`967e41e04fc306fe604e2a693f488995a8b41e5047418f8a5c8e4abd6deca784`；脚本先核对字节及摘要，任一不符即拒绝生成。原始包、数据库、订单标识、客户标识、商家哈希、评价正文、邮编和经纬度都不进入前端资源。

唯一前端数据为`src/dashboardData.json`，紧凑UTF-8编码，不依赖压缩达到体积门槛。本轮实际35,348字节，小于80,000字节；构建时内嵌，访客不下载这个JSON文件。实际摘要和重新生成证据见`evidence/data-checks.json`。这项体积、无运行时数据请求及本地首屏性能可以验证；不能据此承诺任意大陆网络的首次HTTPS连接都在一秒内完成。

## 指标字典

| 指标 | 分子或计算 | 分母及排除条件 |
|---|---|---|
| 总订单数 | 原始订单主表逐笔唯一计数 | 全99,441笔，保留取消、未妥投及缺失商品记录的订单 |
| 时间有效妥投订单 | 最终妥投，且下单、实际收货、承诺收货时间存在；收货不早于下单，承诺日次日零时晚于下单 | 与冻结旧版的晚收货有效性完全一致；不要求所有中间物流节点完整 |
| 准时妥投率 | 有效妥投订单中，实际收货早于承诺日次日零时的订单 | 全部时间有效妥投订单；承诺日当天收货按期 |
| 延迟订单低评分率 | 时间有效且晚收货订单中，有效评分为一至二星的订单 | 同一晚收货集合中有有效一至五星评价的订单；未评价不当作好评 |
| 商品记录金额 | 各商品行的商品价格相加，精确转换为整数分 | 含全部最终订单状态，不含运费，不代表支付结算、净收入或利润 |
| 高危商家金额占比 | 全体商家中，有效妥投样本至少30单且晚收货率不低于15%的商家，其自有商品行金额之和 | 全站全部商品记录金额，既包括非代表商家，也包括样本不足商家；不是只除以30家样本 |
| 品类晚收货率 | 含该中文业务品类商品的去重订单中晚收货数 | 该品类时间有效妥投订单数；同订单跨品类可进入多组，分母不能跨组相加 |
| 商家晚收货率 | 含该商家商品的去重订单中晚收货数 | 该商家时间有效妥投订单数；多商品行只算一单，多商家整单结果不能归因为某一商家的个人责任 |
| 商家客单价 | 商家自有商品行金额之和 | 商家去重订单数；回放门槛专用客单价只用历史截面前已批准的订单，避免使用未来金额 |
| 商家增长率 | 后期去重订单量减前期订单量，再除以前期 | 前期为2018年五月至六月，后期为七月至八月，前期至少20单；全部最终状态，非因果增收效果 |

空分母返回未知值，不用零覆盖缺失。金额使用十进制精确分币，不用浮点相加。所有原始73个非空品类和空品类都有显式中文业务分组；出现未审阅的新原始品类时拒绝生成，禁止把英文或葡萄牙语回退显示到网页。

### 评价去重

评价必须满足评分为一至五星、回答时点不早于下单、评价创建日期不早于下单日期。对同一订单按回答时间降序、创建时间降序、评价标识字典升序、原始行号升序选择首条。没有取最高分、平均分或任意第一条；该规则沿用原冻结处理链。本版选中98,612个订单的有效评分，逐个与冻结数据库核对一致。评价是事后描述结果，不能反推在历史时点已经知道未来评分。

## 三十家代表商家如何确定

先在全体3,095家商家中计算自有商品金额、去重订单、履约分母和增长窗口，不公开真实商家标识。风险分层统一为：有效妥投少于30单为“样本不足”；其余晚收货率至少15%为“高危”，8%至不足15%为“关注”，低于8%为“稳健”。这些是本作品固定的运营核查分层，不是经过真实平台成本优化验证的最优阈值。

1. 高营收高延迟：从37家高危商家中按商品记录金额降序选10家。
2. 高营收高履约：有效妥投至少30单、晚收货率不高于全站晚收货率一半，按商品记录金额降序，排除已选主体后选10家。
3. 高增长：有效妥投至少30单，前期至少20单、后期增长为正，按增长率降序、商品金额降序、原始标识升序做确定性排序，排除已选主体后选10家。

每组恰好10家、总计30家唯一主体，不足时脚本报错而非凑数。对外统一为“商家01”等中文短码及业务代号。主品类按该商家商品金额最多的中文业务组确定，同额按中文名称排序。原始标识只用于离线确定性排序，映射表不输出。三条干预建议是根据本组观察生成的运营核查方案，没有已落地、已降低差评或已提高营收的证据。

四象限横轴为商品记录金额，分界为所选30家金额中位数；纵轴为晚收货率，分界固定15%。四象限比较仅适用于这个代表样本，不能由样本中的象限人数推断整个平台商家分布。

## 延迟分布与“归因”的限制

有效妥投订单分为按期、延迟一至二天、三至五天、六至十天、十一至二十天、二十天以上六组。每组低评分率的分母是该组有有效评分的订单；图中同时提供样本量，样本小的极端箱不能与大箱当作同等可靠。六组订单相加严格等于96,470；中文品类商品金额相加严格等于全站金额。

延迟和低评分相关，但该分布未控制品类、地区、商家质量或订单金额，不能证明延迟造成差评，不能把折线中的拐点当作经过实验确认的因果阈值。

## 可解释规则回放与情景估算

固定回放截面为源数据原始时间2018年3月15日8时，没有另作时区换算。只在30家代表商家的单商家订单中，选取：已在截面前批准、承诺截止在截面之后且落于未来若干天内、截面时尚未看到收货的订单。截止取承诺日期次日零时，区间为截面开、上界闭。商家客单价只从截面之前下单且已批准的订单计算。

- 提前阈值：零至七天，整数步长。
- 商家客单价门槛：零至五百雷亚尔，每五十为一步。
- 预聚合共88个格点，页面只查表并做简单算术，拖动不读文件、不执行全订单筛选。
- 预警命中订单数：满足上述可观察规则的订单数量，不等于最终晚收货预测正确数量。
- 历史差评覆盖：命中订单中，事后时间有效妥投且在截面后回答的一至二星评价数量；已经在截面前发生的差评不能再计作可挽回。
- 情景可挽回差评：历史差评覆盖乘以20%的假设系数。该系数是演示用情景参数，没有实验依据，不是预测概率或真实改善。
- 人工排查成本：命中订单数乘以每单五分钟，再换算小时。该单耗同样是假设，不含系统、沟通或补偿成本。

实际格点的命中订单范围为零至42单，历史差评覆盖为零至16单。零天阈值为空区间，真实输出为零，不伪造结果。示例五天、一百雷亚尔门槛：命中8单，事后有有效评价7单，低评分覆盖5单，情景可挽回1单，排查40分钟。

限制：30家商家以全历史指标事后选样，不能视为当时已经确定的生产监控名单；原始数据缺少取消时间，历史截面可能包含当时已取消而无法识别的订单；观察期及单商家限制会改变可评估样本。新回放器是本次定义的静态情景模型，不能冒用旧版R1—R4的验证结果或声称已在真实业务预测部署。

## 交叉核验与复现

离线脚本从原始CSV独立计算后，只读连接原冻结SQLite，核对以下内容；不调用旧前端或旧API作为唯一真值：

- 全量订单数、有效妥投分母、晚收货数和整数分金额。
- 晚收货有效评价及低评分分子。
- 98,612个订单的最终有效评分逐项相同。
- 全部3,095家商家的去重订单、商品金额、有效妥投和晚收货分子逐项相同，防止商品行或多商家连接放大分母。
- 旧发现窗口全体83,696 / 5,930、收货州RJ的10,891 / 1,436、SP的34,523 / 1,432均保持原值。
- 中文品类和商家商品金额守恒、延迟分组分母守恒、30家唯一且分组数量正确、数据大小小于80,000字节。
- 原冻结数据库在核验前后SHA-256相同；原始ZIP在生成之前按固定来源摘要校验。

在新仓库运行：

```text
python scripts/prepare_dashboard.py --source ../../olist_project --evidence evidence/data-checks.json
python scripts/prepare_dashboard.py --source ../../olist_project --check
python -B -m unittest discover -s tests -p test_dashboard.py -v
```

`--check`只读重算并逐字节比较已有聚合数据，不会重新写数据或回执。默认输出是`src/dashboardData.json`；输出和回执均禁止写入私人原始项目目录。替换数据必须重新审阅固定源摘要和所有口径，不能仅改哈希使校验通过。原ZIP和SQLite不随源码或静态包分发，维护者须在私人环境合法取得原始输入后复现。
